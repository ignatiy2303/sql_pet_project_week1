# SQL_pet_project_week1
## О проекте
### Общее описание проекта

Проект представляет собой реляционную базу данных для хранения и анализа информации о футбольных клубах, игроках, контрактах, соревнованиях и проведённых матчах.
База данных позволяет хранить сведения о футбольных клубах и их стадионах, игроках и их контрактах, соревнованиях и матчах, а также статистику игроков в конкретных матчах.
Основная цель проекта — разработать логически обоснованную реляционную базу данных и продемонстрировать работу с ней с помощью SQL-запросов.
Предметная область проекта — управление футбольным клубом и анализ спортивных и финансовых данных.

## Структура базы данных
В проекте используются следующие таблицы:
- `Players` — информация об игроках.
- `Football_clubs` — информация о футбольных клубах.
- `Stadiums` — информация о стадионах.
- `Contracts` — контракты игроков с футбольными клубами.
- `Competitions` — футбольные соревнования и сезоны.
- `Matches` — информация о матчах.
- `Match_players` — статистика игроков в конкретных матчах.
- `Player_cost_history` — история изменения рыночной стоимости игроков.
Таблица `Match_players` реализует связь многие-ко-многим между игроками и матчами.
Таблица `Player_cost_history` используется для хранения версионных данных об изменении рыночной стоимости игроков и реализует подход SCD Type 2.

## Модели базы данных

### Концептуальная модель
Концептуальная модель показывает основные сущности предметной области и связи между ними без привязки к конкретным типам данных и физической реализации базы данных.

### Логическая модель
Логическая модель содержит таблицы, основные атрибуты, первичные и внешние ключи, а также связи между таблицами.
При построении логической модели схема была приведена к третьей нормальной форме (3НФ).
Основные принципы нормализации:
- каждая таблица описывает отдельную сущность или связь;
- каждый атрибут зависит от ключа своей таблицы;
- повторяющиеся группы данных отсутствуют;
- данные, относящиеся к разным сущностям, разделены по отдельным таблицам;
- связи между сущностями реализованы с помощью внешних ключей.
Для связи игроков и матчей используется таблица `Match_players`, поскольку один игрок может участвовать во многих матчах, а один матч включает нескольких игроков.
Для хранения изменений рыночной стоимости игроков используется `Player_cost_history`.

### Физическая модель
Физическая модель содержит полное описание структуры базы данных: таблицы, атрибуты, типы данных, первичные и внешние ключи, ограничения `NOT NULL`, `DEFAULT` и другие ограничения целостности.

## Версионные данные
Для хранения истории рыночной стоимости игроков используется таблица `Player_cost_history`.
Выбран тип версионирования **SCD Type 2**, поскольку необходимо сохранять не только текущее значение рыночной стоимости игрока, но и историю её изменений.
Для каждой версии хранятся:
- `market_value` — рыночная стоимость;
- `valid_from` — дата начала действия версии;
- `valid_to` — дата окончания действия версии;
- `is_current` — признак актуальной версии.
Таким образом, изменение стоимости игрока не приводит к удалению предыдущего значения, а создаёт новую версию записи.

## Сценарии использования
База данных может использоваться для:

- анализа заработных плат игроков;
- анализа стоимости игроков;
- анализа истории изменения рыночной стоимости;
- анализа результатов матчей;

- анализа футбольных соревнований.

## Скрипты
SQL-скрипты находятся в директории `scripts`.
Основной порядок работы:
1. Создание таблиц базы данных.
2. Создание внешних ключей и ограничений.
3. Заполнение таблиц исходными данными.
4. Заполнение таблицы статистики игроков в матчах.
5. Заполнение исторических данных о рыночной стоимости игроков.
6. Выполнение аналитических SQL-запросов.

### DDL
DDL-скрипты используются для создания структуры базы данных.
Они содержат команды:
- `CREATE TABLE`;
- определение первичных ключей;
- определение внешних ключей;
- ограничения `NOT NULL`;
- `DEFAULT`;

### DML
DML-скрипты используются для заполнения базы данных данными.
В проекте используются команды `INSERT INTO`.

### Аналитические запросы
В проекте реализованы SQL-запросы для анализа данных.
Используются:
- `WHERE`;
- `GROUP BY`;
- `HAVING`;
- `ORDER BY`;
- `INNER JOIN`;
- `LEFT JOIN`;
- `RIGHT JOIN`;
- `FULL JOIN`;
- подзапросы;
- `IN`;
- `ANY`;
- `ALL`;
- `EXISTS`;
- самоcоединение;
- оконные функции;
- `WITH`;
- рекурсивные запросы;
- `LIMIT`;

## Как запустить проект
Для запуска проекта необходим PostgreSQL.
Последовательность запуска:
1. Создать базу данных PostgreSQL.
2. Выполнить DDL-скрипт создания таблиц.
3. Выполнить скрипты заполнения таблиц.
4. Выполнить скрипты аналитических запросов.
После выполнения скриптов база данных будет содержать информацию о футбольных клубах, игроках, контрактах, соревнованиях и матчах.

## Ограничения и целостность данных
Для обеспечения целостности базы данных используются:
- первичные ключи (`PRIMARY KEY`);
- внешние ключи (`FOREIGN KEY`);
- обязательные поля (`NOT NULL`);
- значения по умолчанию (`DEFAULT`);
- составной первичный ключ в таблице `Match_players`.
Составной ключ `player_id + match_id` не позволяет добавить одного и того же игрока в один и тот же матч более одного раза.

## Где можно использовать проект
Разработанная база данных может использоваться как основа для информационной системы футбольного клуба или аналитической системы.
На её основе можно создавать отчёты и аналитические панели для анализа состава команды, финансовых показателей, результатов матчей, статистики игроков и изменения их рыночной стоимости.
